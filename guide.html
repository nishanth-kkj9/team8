The CampusOS API / a step

1APIs in two minutes

An API is a waiter between your app and the data. Your app never goes into the kitchen (the database). It places an order, and the waiter brings back a result.

Every request has four parts

1. Method
POST (the verb: what you want to do)
2. URL
{baseUrl}/api/v1/findit/posts/FND-82067-46fa/claims (the address: what you want to do it to)
3. Headers
Authorization: Bearer eyJhbGciOi... (your ID card, from login) Content-Type: application/json
4. Body
{ "message": "My name is written under the lid" } (the details of your order)

The five methods (verbs)

MethodMeansExample
GETRead, never changes anythingList notices
POSTCreate something new / do an actionRaise a ticket
PATCHChange some fieldsFix a typo in a title
PUTSet / replace one thingSet the turnaround time
DELETERemoveWithdraw a claim

Every response has a status code

CodeIn plain words
2xx (200, 201)It worked. The data is in the body.
4xx (400–429)Something is wrong with your request: missing token, wrong field, not allowed. Read error.code.
5xx (500–504)Problem on the server side. Wait and retry.

2The big picture

There is one shared CampusOS API for the whole hackathon. Each team builds a frontend that talks to it. Each team only ever sees its own institution's data.

Your team = one institution

Every team is a separate "college" with its own email domain. Every account in your team ends with your domain, for example asha@team1.com. The API reads the domain to work out which institution you belong to.

The four feature modules

FindIt

Lost & found. Office staff post items they found, owners claim them.
→ Ch. 7 · Cookbook §4

Notice Hub

Campus notices. Readers ask doubts, the publisher answers.
→ Ch. 8 · Cookbook §5

DocDesk

Request certificates. Student Affairs answers.
→ Ch. 9 · Cookbook §6

FixIt

Maintenance tickets. Campus Maintenance fixes them.
→ Ch. 10 · Cookbook §7

All four modules share the same accounts and login (chapter 4). Base URLs: /api/v1/findit, /api/v1/noticehub, /api/v1/docdesk, /api/v1/fixit.

3Who's who: the actor hierarchy

There are four kinds of users, called roles. The organisers create the admin. The admin creates everyone else. Office staff in two special departments get extra powers.

What each role is, and what we store about them

Admin admin

  • One per team, e.g. admin@team1.com
  • Created from config.json by the organisers
  • Creates, edits and deletes all other users, and can see their OTPs
  • Fields: name, email_id, phone_number

Student student

  • The main users of every module
  • Fields: name, usn, dept, email_id, phone_number
  • USN is unique inside your team and stored in UPPERCASE

Faculty faculty

  • Teachers: post notices, answer doubts, raise tickets, request documents
  • Fields: name, designation, email_id, phone_number

Office staff office_staff

  • Post found items and notices. Their dept can unlock extra powers (below)
  • Fields: name, dept, designation, email_id, phone_number

Office staff departments that unlock extra powers

Office staff with dept =RunsCan do that others can't
Student AffairsDocDeskSee everyone's document requests, answer them, ★ manage document types, ★ set turnaround times
Campus MaintenanceFixItSee everyone's tickets, post progress, resolve, ★ manage issue types, ★ set turnaround times
Anything else (Accounts, Library…)-Normal office staff: post found items, post notices
Spelling matters. The API looks for these two department names. Case doesn't matter, and a trailing "dept" is ignored, so student affairs and Student Affairs Dept both work. StudentAffairs does not work: that user gets 403 FORBIDDEN in DocDesk.

How your app decides what to show

After login, the response contains a profile. Use profile.role, and profile.dept for office staff, to pick which screens and buttons each user sees.

4Accounts and login

Logging in means swapping your email + OTP for a token. The token is your ID card for the next 12 hours. Send it with every other call.

Who creates whom, step by step

One OTP per team. Your team has one OTP, given to you with the admin email. The admin and every user in your team log in with that same OTP, each with their own email. The otp field in the create-user response and in the admin's user list shows this team OTP.

Admin: managing users

Only the admin can create, change or delete users. Users can read their own profile with GET /api/v1/users/me but can't change it.

MethodEndpointWhat it does
POST/api/v1/admin/usersCreate a user. The role field decides which other fields are required.
GET/api/v1/admin/users?role=&limit=&cursor=List users (with OTP), filter by role, page with the cursor
GET/api/v1/admin/users/{email_id}One user
PATCH/api/v1/admin/users/{email_id}Change some fields. The role can't change, and the fields must belong to the role.
POST/api/v1/admin/users/{email_id}/regenerate-otpReturns the user with the team OTP (the OTP is shared, so it doesn't change)
DELETE/api/v1/admin/users/{email_id}Delete the user. Their token stops working.
Rules the API enforces The new user's email must use your domain (otherwise 422 EMAIL_DOMAIN_MISMATCH). The same email or USN twice gives 409 ALREADY_EXISTS. Unknown fields, such as usn for faculty, give 422. Phone numbers have 10–15 digits.

5Set-up order: do this first

Many features need data that someone else creates first. A ticket needs an issue type, and a document request needs a document type. Follow this order once at the start, and every flow in this guide will work.

Tip: keep four tokens handy. Testing a flow usually needs two people, for example a student raises a ticket and Campus Maintenance resolves it. Save a token for each test user and switch between them.

★ Bonus: issue types and the overdue badge

Issue types

Campus Maintenance manages them with POST / PATCH / DELETE /issue-types. Build the "Raise a ticket" dropdown from GET /issue-types instead of hard-coding it. New types then show up right away. Filter the board with GET /tickets?issue_type_id=….

Turnaround time + overdue

PUT /tickets/{id}/tat with {"expected_by": "2026-11-05"} (only while open). If the date passes and the ticket is still open, the ticket shows "overdue": true. Show a red badge for it.

12Patterns you will use everywhere

Lists come in pages

Every list returns {"items": [...], "count": 25, "next_cursor": "..."}, newest first. To get more, call again with ?cursor= set to the next_cursor you received. Stop when next_cursor is null.

Editing with PATCH

  • Send only the fields you want to change
  • Empty body or unknown field → 422
  • Optional text can be cleared with null (JSON) or an empty value (form-data)
  • Remove a file with remove_photo=true, remove_attachment=true…

Files

  • Responses include a url for each file that expires in about 15 minutes. Good for <img src>
  • For download buttons, use the module's download endpoint with the token. It always works
  • The file type is checked from its content, so renaming a file doesn't work

IDs

  • The API creates all IDs. The prefix tells you the type: FND- post, CLM- claim, LST- lost, NTC- notice, DBT- doubt, DTY- doc type, DRQ- request, ITY- issue type, TKT- ticket
  • Users are identified by email_id

Dates and times

  • Dates are YYYY-MM-DD
  • Responses give times in UTC (ending in Z). Convert to IST for display
  • publish_at without a timezone is read as IST
  • Fields with no value are left out, so check before using them

13When things go wrong

Every error looks the same, so write one error handler and reuse it everywhere. Base your logic on error.code, not the message text.

{
  "error": {
    "code": "VALIDATION_ERROR",             // use this in your if/else
    "message": "Request validation failed...", // safe to show to users
    "details": [ { "field": "otp", "message": "String should match pattern..." } ]
  },
  "request_id": "6f1c..."                     // quote this when asking organisers for help
}
Code you'll see mostUsually means
422 VALIDATION_ERRORA field is missing, misspelled or in the wrong format. details names the field.
401 INVALID_TOKENForgot the Authorization: Bearer … header, or sent the token with quotes or extra spaces
403 FORBIDDENRight token, wrong role, for example a student trying to answer a DocDesk request
404 NOT_FOUNDWrong ID, or the record belongs to someone else (you can't see others' records)
409 …The record is in the wrong state for this action, for example acknowledging a ticket that isn't resolved
429 RATE_LIMITEDToo many calls (300 per minute per user) or too many wrong OTPs. Wait for Retry-After seconds

  • FixIt: POST /tickets · GET /tickets · POST …/acknowledge · ★ GET /issue-types

Faculty

  • Everything a student can do (except having a USN), plus:
  • Notice Hub: POST /notices · PATCH/DELETE own · POST /doubts/{id}/response
  • ★ Schedule, pin, archive, attach on own notices

Office staff

  • Everything faculty can do, plus:
  • FindIt: POST/PATCH/DELETE /posts · GET …/claims (all) · /resolution · ★ see all lost requests
  • + Student Affairs: GET /requests (all) · /answer · ★ /doc-types · /tat · /bulk-tat
  • + Campus Maintenance: GET /tickets (all) · PUT …/status · ★ /issue-types · PUT …/tat

Admin

  • POST /auth/admin/login · GET /admin/me
  • Users: POST/GET/PATCH/DELETE /admin/users
  • Notice Hub: post notices, delete any notice, answer any doubt
  • DocDesk: read all requests (read-only)
  • FixIt: read all tickets, delete any ticket
  • FindIt: browse and claim

16Glossary

WordMeaning
APIA set of URLs your app calls to read or change data. Here it is the CampusOS API.
EndpointOne method + URL pair, e.g. POST /api/v1/fixit/tickets.
Base URLThe server address, given by the organisers. Every path in this guide goes after it.
Institution / domainYour team. Every account ends with your team's email domain, e.g. @team1.com.
Roleadmin, student, faculty or office_staff. It decides what a user may do.
OTPThe fixed numeric code used to log in. One per team.
Token (JWT)The long string you get from login. Send it as Authorization: Bearer <token>. It lasts 12 hours.
JSONText format for data: {"name": "Asha"}.
form-dataThe body format used when uploading files (like an HTML form).
Status codeThe number on every response: 2xx OK, 4xx your request has a problem, 5xx server problem.
CursorA bookmark for the next page of a list (next_cursor).
PATCHChange only the fields you send.
TATTurnaround time: the date a request or ticket is expected to be done (expected_by).
AcknowledgeThe requester or reporter confirms they got the document or the fix. This closes the record.
★ Bonus APIOptional extra feature. Finish the core flow first.
/docsThe live interactive API page at {baseUrl}/docs. Try any call in your browser.
Display user text safely. The API stores text exactly as sent. Never insert it as raw HTML. React escapes it for you, so never use dangerouslySetInnerHTML for user text.
Stuck? 1) Read error.code and details. 2) Check the endpoint in the cookbook. 3) Try the same call in {baseUrl}/docs. 4) Ask the organisers and quote the request_id.
